Overview

ZedStack is a business management platform for small and medium-sized businesses in Zambia, such as pharmacies, hardware stores and boutiques.

The first product is an SME Operating System: point of sale, inventory and sales reporting. The long-term plan is a shared platform with more modules, such as agriculture and fleet management, built on the same foundation.

It is in active development and has not launched. This page separates what works today from what is planned.

The problem

Many small shops track stock and sales in notebooks or spreadsheets. That makes it hard to know what is selling, what is running low and what profit is actually being made.

What I built

Working Everything below is built and working today.

  • Multi-tenant accounts. Each business registers and only ever sees its own data. Every record carries a business_id.
  • Secure authentication. Passwords are hashed with bcrypt, and sessions use JWT access tokens.
  • Products and inventory. Add products, restock, get low-stock alerts, and see a stock movement history.
  • Point of sale. Ring up sales with multiple items and payment methods: cash, MTN Mobile Money, Airtel Money and card. Stock reduces automatically, with row locking and validation to prevent overselling.
  • Reports. Revenue, profit (using the cost price recorded at the time of sale), average sale, best-selling products and a payment method breakdown. "Today" is calculated in Zambian time.
  • React web app with login, a sell screen, a stock screen and a reports screen.
  • Database migrations with Alembic, so tables can change without losing data.
  • Containerised local environment with Docker Compose.

Architecture and key decisions

A modular monolith in one monorepo

One backend, one database. Each product (sme, agri, fleet) is meant to be an isolated module, and shared services such as auth, payments, notifications and reporting are meant to be reused across them. Today only the sme module is built.

I chose this over microservices to keep it simple and cheap while the product is being validated.

Multi-tenancy by tenant ID on every table

Every table carries a business ID, and every query filters on it. One business can never read another's records.

Money stored as exact decimals

Amounts are never stored as floats, so totals and profit don't pick up rounding errors.

Migrations from the start

I use Alembic migrations instead of letting the app create tables automatically, so the schema can change without losing data.

Challenges and what I learned

Selling the same stock twice

Two sales at the same time can both see the last item as available. I handled this with row locking and validation when a sale is recorded, so stock can't go negative.

Profit that stays correct

If profit used the current cost price, old sales would change whenever a cost changed. Recording the cost price at the time of sale keeps past profit accurate.

Isolating businesses from each other

With shared tables, one missing tenant filter would expose another business's data. I learned to treat the tenant ID as part of every query, not an extra.

Time zones in reports

"Today's sales" has to mean today in Zambia, not in the server's time zone, so reports calculate the day in Zambian time.
